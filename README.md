# Home Library API

A REST API for managing books, authors, and book loans. The API is built with Django and Django REST Framework and uses PostgreSQL as its database.

## Features

- Create, read, update, and delete authors, books, and borrowing records.
- Associate each book with one required author.
- Track active loans and return timestamps.
- Prevent a book from being borrowed while it already has an active loan.
- List currently available books using a SQL left anti-join.
- Filter, search, sort, and paginate the book list.
- Wrap borrow and return operations in database transactions.

## Data Model

All three models use Django-generated `BigAutoField` primary keys named `id`. IDs are generated by the database and are not supplied when creating records through the API.

### Author

| Attribute | Description |
| --- | --- |
| `id` | Automatically generated primary key |
| `name` | Author's name |
| `biography` | Author biography |
| `created_at` | Automatically recorded creation time |

### Book

| Attribute | Description |
| --- | --- |
| `id` | Automatically generated primary key |
| `author` | Required foreign key to `Author` |
| `title` | Book title |
| `category` | Book category |
| `description` | Book description |
| `created_at` | Automatically recorded creation time |

### BorrowedBook

| Attribute | Description |
| --- | --- |
| `id` | Automatically generated primary key for the loan record |
| `book` | Required foreign key to `Book` |
| `borrower_name` | Name of the borrower |
| `borrowed_at` | Automatically recorded borrowing time |
| `returned_at` | Nullable; empty while the loan is active, populated on return |

### Relationships

- One author can be associated with multiple books. Each book must reference one author through its `author` foreign key.
- One book can have multiple borrowing records over time. Each borrowing record references one book through its `book` foreign key.
- Deleting an author who is referenced by a book is prevented. Deleting a book also deletes its borrowing records.

## Setup

Create and activate a virtual environment, then install dependencies:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Create a PostgreSQL database named `library` and make sure the PostgreSQL server is running. The database connection is configured using environment variables. The defaults are database `library`, user `postgres`, host `localhost`, and port `5432`.

Set the connection values in the terminal where you will run Django. Enter the password at the hidden prompt; do not put it in this README or commit it to source control:

```bash
export PGDATABASE=library
export PGUSER=postgres
export PGHOST=localhost
export PGPORT=5432
read -r -s -p "PostgreSQL password: " PGPASSWORD
printf '\n'
export PGPASSWORD
```

Apply database migrations, optionally create an admin user, and start the development server:

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

The API is available at `http://127.0.0.1:8000/api/`.

## Run with Docker Compose

Docker Compose starts the Django app and PostgreSQL as separate containers. The PostgreSQL data is stored in the named `postgres_data` volume, so it remains after the containers stop or are recreated.

Copy the example environment file and change `PGPASSWORD` to a local development password:

```bash
cp .env.example .env
```

Start the services from the project root:

```bash
docker compose up --build
```

If Docker is being accessed from the VS Code Flatpak terminal, run the command through the host:

```bash
flatpak-spawn --host docker compose up --build
```

The app applies migrations when its container starts and is available at `http://127.0.0.1:8000/api/`. PostgreSQL is available from the host on port `5433` by default; inside Compose, Django connects to the `db` service on port `5432`.

Stop the containers with `docker compose down`. This keeps the database volume. To permanently delete the database data as well, use `docker compose down --volumes`.

## API Endpoints

| Resource | Method | Endpoint | Purpose |
| --- | --- | --- | --- |
| Authors | `GET`, `POST` | `/api/authors/` | List or create authors |
| Author | `GET`, `PUT`, `PATCH`, `DELETE` | `/api/authors/<id>/` | Retrieve, update, or delete an author |
| Books | `GET`, `POST` | `/api/books/` | List or create books |
| Book | `GET`, `PUT`, `PATCH`, `DELETE` | `/api/books/<id>/` | Retrieve, update, or delete a book |
| Available books | `GET` | `/api/books/available/` | List books without an active loan |
| Active loans | `GET`, `POST` | `/api/borrowed-books/` | List active loans or borrow a book |
| Loan | `GET`, `PATCH`, `DELETE` | `/api/borrowed-books/<id>/` | Retrieve, partially update, or delete a returned loan |
| Return a loan | `POST` | `/api/borrowed-books/<id>/return/` | Mark an active loan as returned |

The borrowed-books collection contains active loans only. Returned loan records remain in the database and can still be retrieved by their loan ID. An active loan cannot be deleted; return it first. Trying to borrow a book with an active loan returns `400 Bad Request`. Trying to return a loan that is already returned returns `409 Conflict`.

## Postman Examples

Use `http://127.0.0.1:8000` as the base URL. For requests with a body, select **Body**, **raw**, and **JSON** in Postman.

### Create an author

`POST /api/authors/`

```json
{
	"name": "Ursula Le Guin",
	"biography": "American author of fantasy and science fiction."
}
```

Copy the `id` from the response.

### Create a book

`POST /api/books/`

```json
{
	"author": 1,
	"title": "A Wizard of Earthsea",
	"category": "Fantasy",
	"description": "A young wizard learns magic."
}
```

Replace `1` with the author ID returned by the previous request. The API returns the book ID and a computed `is_available` value.

### Borrow a book

`POST /api/borrowed-books/`

```json
{
	"book": 1,
	"borrower_name": "Alex Reader"
}
```

Replace `1` with the book ID. Save the loan record's returned `id`; that is the loan ID used to return the book.

### Return a book

`POST /api/borrowed-books/<loan-id>/return/`

For example, `POST /api/borrowed-books/12/return/`. No request body is required. The API sets `returned_at`, removes the loan from the active-loans list, and makes its book available again.

## Filtering, Searching, Sorting, and Pagination

The `GET /api/books/` endpoint is the book collection or list endpoint. It supports these query parameters:

| Parameter | Example | Behavior |
| --- | --- | --- |
| `title` | `?title=earth` | Case-insensitive partial match on title |
| `category` | `?category=Fantasy` | Case-insensitive exact match on category |
| `search` | `?search=wizard` | Searches title, category, and description |
| `ordering` | `?ordering=title` | Sorts by title ascending |
| `ordering` | `?ordering=-created_at` | Sorts by creation time descending |
| `page` | `?page=2` | Selects a page of results |

Supported sort fields are `id`, `title`, `category`, and `created_at`. The default order is newest first. The list endpoints for books and available books return five books per page. Paginated responses include `count`, `next`, `previous`, and `results`.

## Indexing and SQL Joins

In this project, “book index” refers to the collection endpoint `GET /api/books/`; it does not mean that custom database indexes were added. Django automatically indexes primary keys and foreign-key columns. No custom indexes were defined for title, category, or creation time.

The available-books query in `books_api/views.py` uses Django's `FilteredRelation` to left-join books to active borrowing records, where `returned_at` is `NULL`. The available-books endpoint then filters for rows where the joined loan ID is `NULL`. This is a left anti-join: it returns books with no active loan.

The active-loans endpoint filters borrowing records where `returned_at` is `NULL`. Once a loan is returned, it no longer appears in that collection, but its record is retained for history.

## Transactions and Availability

Transactions are separate from the left join. The join is used to query available books; transactions protect changes made while borrowing or returning a book.

Borrowing uses `transaction.atomic()` and locks the book row with `select_for_update()`. It checks for an active loan before creating a borrowing record. Returning a book also runs atomically, locks the loan and book rows, and sets the loan's `returned_at` timestamp. This prevents partial updates and helps avoid concurrent requests creating multiple active loans for the same book.

Availability is derived from active borrowing records rather than stored in a separate `Book` database column.
